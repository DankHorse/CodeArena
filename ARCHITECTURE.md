# Architecture

## Scope and verified tiers

This repository implements the DOGFOOD T1 event, team, project, and gallery
flow, and the T2 event-scoped judging flow. The submission claims and official
acceptance result are **T1 and T2 verified**. No T3 or T4 capability is claimed
here.

The code challenge system is a separate domain: `Problem`, coding
`Submission`, `SubmissionTestResult`, and the evaluation worker do not serve
or store DOGFOOD project judging data. DOGFOOD projects are
`ProjectSubmission` rows and are evaluated by human judges.

## Runtime layout

- `backend/app/api/routes/` exposes FastAPI routes and mounts them under
  `/api/v1` (`/health` is the health check).
- `backend/app/schemas/` defines validated request and response shapes.
- `backend/app/dependencies/` resolves authenticated users and enforces roles
  and event-scoped authorization.
- `backend/app/services/` contains business operations for auth, events,
  teams, projects, judging, coding submissions, problems, and statistics.
- `backend/app/models/` contains SQLAlchemy models; `backend/migrations/`
  applies schema changes through Alembic.
- `backend/app/worker/` evaluates coding submissions separately from DOGFOOD
  human judging.
- `backend/app/scripts/seed_dogfood.py` loads the organizer fixture and writes
  local acceptance credentials.
- `backend/app/tests/` contains backend API and behavior tests, including T1
  and T2 DOGFOOD tests.
- `frontend/` is the existing Vite/React frontend. It is not required by the
  API acceptance checker.
- Root `fixtures.json` and `run.py` are organizer-provided acceptance inputs;
  `run.py` checks the configured portal and role headers.

`backend/docker-compose.yml` starts PostgreSQL and the backend. The
backend container applies migrations, seeds the DOGFOOD fixture, then serves
the API. The local config `.dogfood.local.toml` is generated by this workflow,
contains local-only credentials, and must not be committed.

## Authentication and role isolation

Login issues a JWT in an HttpOnly cookie. The API validates its signature,
issuer, expiry, and token use, then loads an active user. Public registration
creates a `participant`; there is no public self-promotion. An admin can assign
participant or organizer roles. The global user roles are `participant`,
`organizer`, and `admin`.

Authorization is checked by the backend. Event management is scoped to the
event's `organizer_id`, including when the actor is a global admin. Judging
adds an event-specific judge assignment: a judge remains a global participant
but is authorized as a judge only for the assigned event. A judge can read and
write only their own assignments and evaluations. Participants cannot use
judge routes. Organizers can see assignment progress and aggregate results,
but not individual score sheets or feedback. These checks do not depend on the
frontend hiding controls.

## Main request flows

1. A participant registers for an event, creates or joins a team, and the
   captain creates and finalizes a project before the event deadline.
2. Public gallery reads expose submitted projects from eligible event states
   without team or user identities.
3. An event organizer creates and activates a rubric, enrolls judges, and
   assigns submitted projects. Judges save and submit their own evaluations.
4. The organizer reads progress, recalculates a versioned result snapshot, or
   exports event-scoped results as CSV.

Database constraints and service checks enforce event relationships and
uniqueness. The T2 details and normalization formula are in
[JUDGING.md](JUDGING.md); table relationships are in
[DATA-MODEL.md](DATA-MODEL.md).

## Local acceptance

Configure `backend/.env` using `backend/.env.example`, then from the repository
root start the local stack:

```sh
docker compose --env-file backend/.env -f backend/docker-compose.yml up --build
python3 run.py .dogfood.local.toml
```

The official acceptance result is **T1/T2 verified**, with all three T1 and
all four T2 checks passing. The generated `.dogfood.local.toml` contains
short-lived local credentials and must not be committed. See
[backend/README.md](backend/README.md) for backend setup and API documentation.
